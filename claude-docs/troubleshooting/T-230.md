# T-230 · 미커밋 작업 중 `git checkout -- <file>`은 그 파일의 작업분을 통째로 지운다

- **증상**: 2분할 로테이션(PR 2)을 구현한 뒤 돌연변이 테스트를 돌리는 중이었다. `exercises.ts`의
  `unitOf`에 돌연변이를 심어 테스트가 죽는 것을 확인하고, 되돌리려고 이렇게 했다.

  ```
  git checkout -- miniapp/src/data/exercises.ts
  ```

  명령은 **아무 말 없이 성공**했다. 그런데 되돌아온 것은 돌연변이 직전 상태가 아니라
  **HEAD 상태**였다 — 그 파일에 있던 `Unit`·`UNIT_KEYS`·`UNIT_OF`·`unitOf`가 전부 사라졌다.
  다음 테스트 실행에서 `unitOf is not a function`이 무더기로 떠서야 알아챘다.

- **원인**: `git checkout -- <path>`는 **인덱스(스테이지)의 내용으로 워킹트리를 덮어쓴다.**
  스테이지에 아무것도 없으면 HEAD가 그 자리를 대신한다. 「방금 한 편집만 취소」하는 명령이
  아니라 **「이 파일의 미커밋 변경을 전부 버린다」**는 명령이다.

  돌연변이 테스트의 맥락이 함정을 키운다 — 이때 워킹트리에는 **커밋 안 된 구현 전체**가 들어
  있고, 되돌리려는 것은 그중 방금 심은 **한 줄**뿐이다. 둘의 크기 차이를 명령이 구분해 주지 않는다.
  게다가 실패가 **조용하다**: 삭제된 것은 diff에도 에러에도 안 뜨고, 나중에 엉뚱한 곳에서
  `is not a function`으로 나타난다.

- **해결**: 돌연변이는 **심은 것과 같은 방법으로 되돌린다** — Edit 도구(또는 에디터)로 그 한 줄을
  원래대로 되돌려 쓴다. 되돌릴 내용을 손에 쥐고 있으니 git을 부를 이유가 애초에 없다.

  git으로 안전망을 두려면 checkout이 아니라 **stash에 이름표를 달아** 둔다.

  ```
  git stash push -m "2분할 구현 - 돌연변이 전"    # 심기 전에 대피
  git stash pop                                  # 확인 뒤 복구
  ```

  이미 날린 뒤라면 커밋 전이라 reflog에도 없다 — **다시 쓰는 수밖에 없다.**

- **재발방지**: **미커밋 작업이 있는 파일에는 `git checkout -- <file>`·`git restore <file>`을
  쓰지 않는다.** 이 명령들의 대상은 「버려도 되는 변경」이지 「방금 한 변경」이 아니다.

  판별 기준 한 줄: **되돌리려는 것이 그 파일의 미커밋 변경 *전부*가 아니라면 git은 도구가 아니다.**
  일부만 되돌리는 것은 편집이지 버전 관리가 아니다.

  돌연변이 테스트처럼 **일부러 코드를 망가뜨렸다가 되돌리는 절차**는 특히 위험하다 — 되돌리기가
  절차의 정상 단계라서 방심하게 된다. 그 절차를 시작하기 전에 커밋하거나 `stash push -m`으로
  대피시켜 두면, 되돌리기를 실수해도 잃을 것이 없다.
