# T-218 · 약한 검사기를 통과한 것은 아무것도 증명하지 않는다 (appName)

- **증상**: `apps-in-toss.config.ts`에 `appName: '홈트가어렵나'`(한글)를 넣고 `npm run release`를 돌렸다. **빌드가 통과했고** `홈트가어렵나.ait`(109KB)가 정상으로 나왔다. 이걸 근거로 changeLog에 *"한글 `appName`이 그대로 통과하는 것도 실측으로 확인했다"* 고 적었다.

  실제로는 배포도, 실행도 안 되는 값이었다. 앱인토스 콘솔 등록 화면이 `appName`을 *"수정할 수 없는 고유 ID예요"* 라고 표시해서 다시 파 보고서야 드러났다 — **되돌릴 수 없는 필드에 이 값을 넣기 직전이었다.**

- **원인**: 빌드의 `appName` 검증이 이것뿐이다.

  ```js
  // node_modules/@apps-in-toss/cli/dist/index.js:344
  if (typeof config.appName !== "string" || config.appName.trim() === "") {
  ```

  형식은 아예 안 본다. 정작 실제 제약은 **다른 두 곳**에 있었다.

  ```js
  // index.js:1055 — ait init의 대화형 입력 검증
  if (value !== kebabCase(value)) return `앱 이름은 케밥-케이스 형식이어야 합니다 (예시: ${kebabCaseValue})`;

  // index.js:676 — appName이 URL의 host 자리에 그대로 박힌다
  `intoss-private://${appName}?_deploymentId=${deploymentId}&host=appsInTossHost`

  // index.js:512 — 업로드 API의 경로 세그먼트로도 그대로 들어간다
  `${baseUrl}/api-public/v3/openapi/bundles/${config.appName}/upload-start`
  ```

  즉 `appName`은 **표시 이름이 아니라 URL에 박히는 식별자**다. `ait init`으로 만들었으면 케밥-케이스 검증에 걸려 애초에 막혔을 텐데, 설정 파일을 손으로 쓰면서 그 검증을 **우회해 버렸다.** 빌드는 그 우회를 잡아 줄 만큼 촘촘하지 않았다.

- **해결**: 표시 이름과 ID를 분리했다.

  | 자리 | 값 | 수정 |
  |---|---|---|
  | 콘솔 「한국어 앱 이름」 | `홈트가어렵나` | 가능 |
  | 콘솔 `appName` = 설정의 `appName` | `home-workout-hard` | **불가** |

  아티팩트도 `home-workout-hard.ait`로 바뀐다. **이름을 바꾸면 옛 아티팩트를 반드시 지운다** — `ait deploy`는 `<appName>.ait`를 찾는 게 아니라 *"현재 패키지 루트 디렉토리에서 발견되는 첫 .ait 파일"* 을 올린다(index.js:138). 둘이 공존하면 **옛 번들이 배포될 수 있다.** `*.ait`는 gitignore 대상이라 PR 리뷰에도 안 잡힌다.

- **재발방지**: **검사기가 통과시킨 것은 「검사기가 그걸 안 본다」는 뜻일 수도 있다.** 통과를 근거로 삼기 전에 **그 검사기가 무엇을 보는지**를 확인한다 — 여기서는 소스 20줄을 읽는 데 1분이 걸렸고, 그 1분이 수정 불가 필드를 살렸다.

  판별 신호는 **「통과했다」와 「쓰이는 곳의 제약」이 어긋나는 것**이다. 값이 URL·파일명·DB 키처럼 **다른 문법을 가진 자리로 흘러가면**, 그 자리의 문법을 직접 확인해야 한다. 생성기(`ait init`)를 우회해 설정을 손으로 썼다면 특히 그렇다 — 생성기에만 있던 검증을 함께 건너뛴 것이다.

  글로벌 「번들 문자열 검사」 원칙과 **같은 종류**다: 거기서는 grep이 양방향으로 고장 난 계측기였고, 여기서는 빌드 검증이 그랬다. 공통 교훈은 *계측기의 통과를 사실로 승격하지 말 것*.
