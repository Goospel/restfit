# T-240 · CRLF 파일에 `\n` 치환은 무적용 무성 실패 — 돌연변이 「생존」 오판

- **증상**: 확대 금지 가드(PR #60)의 돌연변이 실측에서, `index.css`의 선언을 다른 블록으로
  옮기는 치환 스크립트를 돌리고 테스트를 실행했더니 **전부 통과**했다. 겉보기에는
  「돌연변이 생존 = 테스트가 공허하다」는 판정 로그와 구별이 안 된다 — 실제로는
  **치환이 한 글자도 적용되지 않은 원본**을 테스트한 것이었다.

- **원인**: 파일이 CRLF(`\r\n`)인데 치환 패턴이 `\n`만 기대했다. 여러 줄에 걸친 매칭이
  `\r` 때문에 실패했고, 치환 0건은 에러가 아니라서 스크립트는 성공으로 끝났다.
  멀티바이트 한글이 아니라 **개행 바이트**가 원인이라는 점만 다를 뿐, 「Git Bash
  grep/sed 멀티바이트 무성 실패」(글로벌 원칙 1)와 같은 꼴이다 — 패턴 불일치가
  에러 없이 0건 처리되고, 0건이 성공처럼 보인다.

  같은 리뷰에서 부수 발견된 이웃 함정: Git Bash 파이프라인(`grep -c $'\r'`,
  `sed | od`)은 CRLF 파일에서 **CR을 안 보이게 지운다** — CRLF 75개짜리 파일이
  0으로 나온다. 즉 Git Bash로는 치환도 판정도 CR 앞에서 조용히 틀린다.

- **해결**: 치환 스크립트에 **적용 가드**를 넣었다 — 치환 전후 내용을 비교해 같으면
  즉시 실패(`if (c === before) exit 1`). 가드가 무적용을 잡아낸 뒤 CRLF를 감안한
  패턴으로 재실행해 정상 측정했다. EOL 판정 자체는 PowerShell
  `[IO.File]::ReadAllBytes` 바이트 대조로 했다(Git Bash 파이프라인 배제).

- **재발방지**: **돌연변이(또는 어떤 자동 치환이든)를 「적용됐다」고 믿지 않는다 —
  적용 여부를 실행으로 확인한 뒤 측정한다.** 구체적으로 둘 중 하나를 매번 찍는다.

  ```sh
  git diff --stat        # 비어 있으면 치환이 안 된 것 — 측정 중단
  ```

  또는 스크립트 안에서 치환 전후 문자열 비교 가드. [T-239](T-239.md)가 「복원됐다」를
  실행으로 확인하는 규율이라면, 이번 것은 그 대칭인 **「적용됐다」 확인**이다 — 돌연변이
  측정은 적용·복원 양 끝을 모두 실측해야 계측기가 된다. [T-236](T-236.md)과 같은
  묶음: **하네스의 출력은 그 하네스가 실제로 무엇을 실행했는지의 증거가 아니다.**

  이 함정은 CRLF가 기본인 Windows 레포 어디서든 재발한다 — 글로벌 「Windows 셸
  한글·인코딩 원칙」의 무성 실패 군(패턴 불일치 → 0건 → 성공처럼 보임)에 개행
  바이트 사례로 추가할 승격 후보.
