# T-216 · 기계 설정과 코드 가정이 같으면 테스트가 공허해진다

- **증상**: `todayKey()`가 한국 시간 기준 `YYYY-MM-DD`를 주는지 검증하는 테스트를 썼고 통과했다.

  ```ts
  export function todayKey(date = new Date()): string {
    return date.toLocaleDateString('sv-SE', { timeZone: 'Asia/Seoul' });
  }

  it('한국 시간 기준 날짜를 준다', () => {
    expect(todayKey(new Date('2026-08-24T20:00:00Z'))).toBe('2026-08-25'); // KST 익일 05:00
  });
  ```

  돌연변이 검증에서 **`{ timeZone: 'Asia/Seoul' }`을 통째로 지웠는데 테스트가 그대로 통과했다.** 다른 13종은 전부 사살됐는데 이것만 살아남았다.

- **원인**: **개발 기계의 로컬 시간대가 이미 KST다.** `toLocaleDateString`은 옵션이 없으면 시스템 시간대를 쓰므로, 이 기계에서는 지정이 있으나 없으나 **정확히 같은 값**이 나온다. 테스트는 "KST 처리"를 검증하는 것처럼 생겼지만 실제로는 **"이 기계의 시간대에서 날짜가 나온다"** 만 검증하고 있었다.

  UTC로 도는 CI나 다른 시간대의 기계에서 돌리면 그때서야 깨진다. 사용자는 한국에 있으니 실제 사용자 피해는 없었겠지만, **테스트가 지키고 있다고 믿은 것을 실제로는 안 지키고 있었다.**

  같은 함정이 로케일·통화·인코딩·주 시작 요일에도 그대로 있다. 공통 구조는 **「기계 기본값 == 코드가 지정한 값」이면 지정을 지워도 결과가 같다**는 것이다.

- **해결**: 환경 의존 값을 **인자로 빼고, 다른 값에서 답이 달라지는지**를 본다. 기대값 하나만 보면 영원히 못 잡는다.

  ```ts
  export function todayKey(date = new Date(), timeZone = 'Asia/Seoul'): string {
    return date.toLocaleDateString('sv-SE', { timeZone });
  }

  it('시간대를 실제로 적용한다', () => {
    const d = new Date('2026-08-24T20:00:00Z');
    expect(todayKey(d, 'Asia/Seoul')).toBe('2026-08-25');
    expect(todayKey(d, 'UTC')).toBe('2026-08-24'); // ← 이 줄이 돌연변이를 죽인다
  });
  ```

- **재발방지**:
  1. **시간대·로케일·통화·인코딩을 다루는 코드는 그 값을 인자로 뺀다.** 테스트 편의가 아니라 **테스트가 가능해지기 위해서**다. 하드코딩된 환경 값은 그 환경에서 검증할 수 없다.
  2. **대조군 없는 단정은 환경 의존 코드에서 무의미하다.** "A를 넣으면 X" 하나가 아니라 **"B를 넣으면 Y"** 를 같이 둔다.
  3. **돌연변이 검증이 이걸 잡은 유일한 수단이었다.** 테스트가 통과한다는 사실만으로는 테스트가 뭘 지키는지 알 수 없다. 새 순수 함수를 만들면 돌연변이를 한 번 돌린다.
  4. 글로벌 CLAUDE.md 「번들 문자열 검사 — 항상 통과 쪽 고장」과 같은 계열이다. **계측기가 늘 초록인 것과 지킬 게 없는 것은 구분되지 않는다.**
