# T-239 · 돌연변이 복원이 조용히 실패해 6종이 누적됐다 — 「사살처럼 보이는」 누적 실패

- **증상**: 목표 반복 범위 이탈 안내(PR #56)의 돌연변이 실측을 한 셸 블록에서 6종 연속으로
  돌렸다. 결과가 이렇게 나왔다.

  ```
  --- M1: !bodyweight 가드 제거      Tests  1 failed | 23 passed (24)
  --- M2: 경계 포함->배타            Tests  2 failed | 22 passed (24)
  --- M3: 구간 숫자 하드코딩          Tests  3 failed | 21 passed (24)
  --- M4: shorthand 대신 borderColor  Tests  4 failed | 20 passed (24)
  --- M5: 미달 분기 제거             Tests  5 failed | 19 passed (24)
  --- 복원 확인                      Tests  5 failed | 19 passed (24)
  ```

  **매 단계 정확히 +1씩 늘어난다.** 겉보기에는 「돌연변이마다 테스트 하나씩 죽는다」는
  이상적인 사살 로그와 **구별이 안 된다** — 실제로는 돌연변이가 하나도 안 지워진 채 계속
  쌓이고 있었다. 마지막 「복원 확인」이 24 passed가 아니라 5 failed로 찍혀서야 드러났다.
  각 반복 사이에 `cp: cannot stat '../W.bak': No such file or directory`가 찍혀 있었지만
  vitest 출력에 섞여 흘러갔다.

- **원인**: 백업 줄이 이랬다.

  ```sh
  cp $F /tmp/W.bak 2>/dev/null || cp $F ../W.bak   # 백업
  ...
  cp ../W.bak $F                                    # 복원
  ```

  **`||`는 앞 명령이 실패할 때만 뒤를 실행한다.** Git Bash에는 `/tmp`가 있어서 앞엣것이
  성공했고, 그래서 `../W.bak`은 **한 번도 만들어지지 않았다.** 그런데 복원은 `/tmp/W.bak`이
  아니라 **`../W.bak`을 하드코딩**하고 있었다 — 백업은 A에 쓰고 복원은 B에서 읽는,
  **경로가 갈라진 짝**이었다. `cp`가 낸 에러는 exit 1로 끝났지만 `set -e`가 없었고 그 값을
  아무도 안 봐서 루프가 그대로 다음 돌연변이로 넘어갔다.

  ⚠️ **여기부터는 추정이다**: 최초에 `/tmp` 가용성이 불확실하다고 보고 폴백을 붙였는데,
  복원 줄을 폴백 경로로만 쓰고 백업의 「성공한 쪽」과 맞추지 않은 것으로 보인다. 즉
  **폴백을 추가한 순간 복원이 두 경로를 모두 감당해야 했는데 그러지 않았다.** 이 부분은
  당시 의도를 사후에 재구성한 것이라 확정이 아니다. 관측된 사실은 위의 「경로가 갈라졌다」뿐이다.

- **해결**: 복원을 백업과 **같은 경로 한 곳**으로 고정하고(`/tmp/W.bak`), 6종을 개별로
  다시 측정했다 — 각 돌연변이가 **정확히 겨눈 테스트 1건씩만** 죽는 것으로 결과가 바뀌었다
  (매번 `Tests 1 failed | 23 passed`). 누적 로그의 「+1씩 증가」는 사살이 아니라
  **누적의 모양**이었다.

  더 나은 처방: 이 레포처럼 **대상 파일이 이미 커밋돼 있고 미커밋 변경이 돌연변이뿐**이면
  백업 파일을 아예 만들지 않고 `git checkout -- <file>`로 되돌리는 것이 짧고 안전하다.
  단 그 전제가 깨지면 정반대 사고가 난다 — [T-230](T-230.md) 참조(미커밋 구현이 있는
  파일에 쓰면 작업분이 통째로 날아간다). **두 함정은 방향이 반대라 전제를 먼저 확인해야
  어느 쪽이 맞는지 갈린다.**

- **재발방지**: **돌연변이를 되돌린 뒤 「되돌아왔다」를 실행으로 확인한다.** 복원 명령이
  성공했다고 믿지 않는다 — 이번 사고에서 실패한 것은 판단이 아니라 `cp` 한 줄이었다.
  매 복원 뒤 두 가지를 찍는다.

  ```sh
  git status --porcelain          # 대상 파일이 목록에 없어야 한다
  git hash-object <file>          # HEAD의 blob과 같아야 한다
  git rev-parse HEAD:<file>
  ```

  **`git status`만으로 부족한 경우가 있다** — 대상 파일이 애초에 미커밋이면 복원 전후
  둘 다 ` M`이라 상태가 안 변한다. blob 해시 대조가 그 구멍을 메운다.

  그리고 **로그의 모양으로 사살을 판정하지 않는다.** 「실패 수가 단조 증가한다」는
  이상적 사살 로그와 누적 사고가 **같은 모양**이라, 사살의 근거는 개수가 아니라
  **매 단계 `1 failed`로 돌아오는가**와 **죽은 테스트의 이름이 겨눈 것과 일치하는가**다.
  가능하면 돌연변이를 **한 번에 하나씩** 돌려 사이마다 클린 상태를 통과시킨다.

  계측기 자체가 거짓말하는 유형이라 [T-236](T-236.md)(하네스가 실행 실패를 「전부 생존」으로
  보고)과 한 묶음이다 — **하네스의 출력은 그 하네스가 실제로 무엇을 실행했는지의 증거가
  아니다.** 셸 폴백(`||`)을 붙일 땐 **그 폴백이 만든 분기를 소비하는 쪽까지** 함께 고친다.
