# T-220 · 올린 이미지가 조회에 안 보인다 (검토 승인 후 반영)

- **증상**: `miniapp_update_screenshots`로 스크린샷 4장 + 썸네일 1장을 올렸다. 업로드는 **5장 모두 HTTP 200**이었고 전송 바이트도 파일 크기와 정확히 일치했다. 그런데 곧바로 `miniapp_get`을 부르니 **`images`가 빈 배열**이었다.

  같은 요청으로 함께 보낸 `detailDescription`은 **즉시 반영돼 있었다.** 한 요청에서 텍스트는 들어가고 이미지만 안 들어간 꼴이라, 이미지가 거부된 것처럼 보였다.

- **원인**: 이미지는 **앱정보 검토가 승인되는 시점에 반영된다.** 요청 직후 상태는 이랬다.

  ```
  reviewState: IN_REVIEW    isEditable: false    images: []
  ```

  승인 뒤 같은 조회를 하니 5장이 `displayOrder` 0~4로 전부 들어와 있었다. **요청은 처음부터 정상이었다.**

  판별에 쓸 수 있었던 신호가 하나 있었다 — 같은 워크스페이스에서 `PREPARE`인 미니앱은 `images: []`이고, `OPEN`인 것들(북타이머·딥시그널)은 값이 있었다.

- **해결**: 기다린다. `isEditable: false`라 어차피 그 사이에는 손댈 수도 없다.

  ⚠️ 이때 「실패했나 보다」 하고 다시 올리면 **같은 이미지가 중복 업로드**되고, 검토 요청도 한 번 더 들어간다.

- **재발방지**: **`miniapp_get`의 `images`로 업로드 성공을 판정하지 않는다.** 판정 근거는 PUT의 HTTP 200과 전송 바이트 수이고, 조회 반영은 `reviewState`가 `APPROVED`가 된 뒤에 확인한다.

  덤으로 알게 된 것: 요청에 넣은 `backgroundColor`는 무시된다. 전부 `#F2F4F6`으로 보냈는데 저장된 값은 `#F4F4F5`·`#F2F3F3`·`#F8F8F8`·`#F7F7F7`로 제각각이었다 — **토스가 이미지에서 실제 색을 자동 추출**한다. 이 필드를 맞추려고 애쓸 필요가 없다.
