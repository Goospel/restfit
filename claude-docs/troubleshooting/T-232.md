# T-232 · jsdom + fake-indexeddb에서는 Blob이 왕복하며 정체를 잃는다

- **증상**: 촬영 화면 테스트(jsdom)에서 사진 1장을 `fake-indexeddb`에 넣고 화면을 띄웠는데
  고스트 오버레이가 **끝내 안 뜬다.** 실루엣 가이드(사진 0장 분기)만 계속 그려졌다.
  같은 저장소를 쓰는 `photoStore.test.ts`(node 환경)는 **16건 전부 초록**이라 저장소는
  무죄로 보였고, 화면의 분기 조건부터 의심하게 된다.

- **원인**: `fake-indexeddb`의 구조화 복제가 **jsdom의 `Blob`을 모른다.** 넣을 때는 진짜
  Blob이라 `savePhoto`가 `'ok'`를 돌려주는데, `getAll`로 꺼내면 생성자가 `Object`인
  **평범한 객체**로 돌아온다(`blob instanceof Blob === false`). `photoStore`의 읽기 쪽
  어휘 검증(`isPhoto`)이 그걸 손상 레코드로 보고 걸러서 **목록이 항상 빈다.**

  ```
  RAW [ { ctor: 'Object', isBlob: false } ]   // jsdom 환경
  ```

  node 환경에서는 전역 `Blob`이 Node의 것이고 복제기가 그걸 알아서 왕복이 멀쩡하다 —
  그래서 **저장소 테스트는 초록인데 화면 테스트만 빈 목록을 본다.** 실제 브라우저의 IDB는
  진짜 Blob을 돌려주므로 이건 **테스트 환경만의 함정**이지 제품 결함이 아니다.

- **해결**: jsdom 화면 테스트에서는 `listPhotos`를 목으로 두고 픽스처 배열을 준다
  (`BodyPhoto.test.tsx`). 저장소의 진짜 왕복은 node 환경의 `photoStore.test.ts`가 잰다 —
  **환경마다 잴 수 있는 것을 재고, 못 재는 것은 다른 환경에 맡긴다.** `openPhotoDb`는 화면의
  분기(「IDB가 없으면 안내」)라서 목으로 갈지 않고 진짜를 쓴다.

- **재발방지**: **jsdom 테스트에서 IDB에 Blob을 왕복시키지 않는다.** 비교 화면(PR C)도 같은
  벽을 만난다 — 사진 목록이 필요하면 저장소 함수를 목으로 두고 픽스처를 준다. 증상이
  「목록이 비어 있다」로 나타나므로, 화면 분기를 의심하기 전에 **저장소가 무엇을 돌려주는지
  한 줄 찍어 보는 것**이 가장 빠른 감별이다(`blob instanceof Blob`).
