# T-234 · fake-indexeddb 내부 클래스는 import하면 타입이 안 따라온다

- **증상**: 화면이 언마운트에 `IDBDatabase.close()`를 부르는지 재려고
  `import FDBDatabase from 'fake-indexeddb/lib/FDBDatabase'`를 썼다. **테스트는 돌았는데
  `npx tsc -b`가 막았다**:

  ```
  TS7016: Could not find a declaration file for module 'fake-indexeddb/lib/FDBDatabase'.
  There are types at '.../fake-indexeddb/lib/FDBDatabase.d.ts',
  but this result could not be resolved when respecting package.json "exports".
  ```

- **원인**: 패키지의 `exports` 맵이 `./lib/FDBDatabase`에 `import`/`require`만 두고 **`types`를
  안 둔다**(루트 `.`에만 있다). `.d.ts` 파일은 디스크에 **있는데도** exports를 존중하는 해석에서는
  닿을 수 없다 — 라이브러리 쪽 문제라 우리가 고칠 수 없고, `moduleResolution`을 낮추는 것은
  이 레포 전체의 해석 규칙을 바꾸는 일이라 대가가 크다.

- **해결**: **내부 클래스를 import하지 않고 실제 인스턴스에서 프로토타입을 꺼낸다.** 공개
  API(`openPhotoDb`)로 연결 하나를 열고 그 프로토타입에 스파이를 건다 — 같은 프로토타입을
  모든 인스턴스가 공유하므로 화면이 연 연결의 `close()`도 잡힌다.

  ```ts
  const db = await openPhotoDb(new IDBFactory() as IDBFactory);
  const close = vi.spyOn(Object.getPrototypeOf(db!) as IDBDatabase, 'close');
  ```

  (화면이 연 연결의 핸들은 밖에서 잡을 수 없어 **프로토타입에 거는 것 자체는 필요하다** —
  피한 것은 내부 모듈 import뿐이다. 다 쓴 뒤 `close.mockRestore()`.)

- **재발방지**: **테스트 더블의 내부 모듈을 직접 import하기 전에 그 패키지의 `exports`에
  `types`가 있는지 본다.** 없으면 공개 API로 만든 인스턴스에서 필요한 것을 꺼낸다 —
  `vitest`는 타입을 안 보고 돌기 때문에 **테스트가 초록이어도 `tsc`에서 막힌다.** 화면 테스트를
  추가한 뒤에는 `npx vitest run`만이 아니라 **`npx tsc -b`도 같이** 돌린다.
