# T-246 · `.ait` 번들 문자열 검사 — ZipFile로 바로 열면 엔트리 0개가 조용히 나온다

- **증상**: 검수에 올리기 전 번들 실물에 수정이 들어갔는지 확인하려고([T-224](T-224.md)에서
  얻은 규칙) `home-workout-hard.ait`를 zip으로 열어 문자열을 대조했다.

  ```powershell
  Add-Type -AssemblyName System.IO.Compression.FileSystem
  $z = [System.IO.Compression.ZipFile]::OpenRead($aitPath)
  foreach ($e in $z.Entries) { ... }   # ← 한 번도 안 돈다
  ```

  **예외도 에러도 없이** 엔트리 루프가 0회 돌고 누적 문자열이 0자가 된다. 그 상태로 마커를
  대조하면 **전부 `False`** 다 — 새 기능 문구도, 기존 기능 문구도, 개발용 입구도 똑같이 없다.

  ⚠️ **이게 정확히 「항상 실패 쪽으로 고장 난 계측기」다**(글로벌 「번들 문자열 검사」 원칙).
  대조군을 안 두면 「번들에 수정이 안 들어갔다」로 읽고 멀쩡한 번들을 다시 뽑느라 시간을 태운다.

- **원인**: `.ait`는 zip이 **아니다.** 파일 머리를 보면 자체 매직이 있다.

  ```
  head hex : 41 49 54 42 55 4e 44 4c 00 00 00 01 00 00 00 00
  head text: AITBUNDL ....... $01a06630-6fc6-7837-bcc4-78863f3a374a home-workout-hard {package.json...}
  ```

  `AITBUNDL` 매직 + 길이 필드 + **deploymentId** + appName + `package.json` 사본이 앞에 오고,
  **그 뒤에 진짜 zip이 통째로 붙어 있다**(이 번들에서는 `PK\x03\x04`가 오프셋 **2131**).
  `ZipFile.OpenRead`는 파일 끝에서 central directory를 찾아 열기 때문에 **예외 없이 열리고**,
  다만 앞쪽 오프셋이 어긋나 엔트리가 안 잡힌다 — 그래서 **에러가 아니라 빈 결과**로 끝난다.

  > deploymentId가 헤더에 박혀 있다는 것이 plan.md의 *"`ait build`가 번들 헤더에 심은 값을
  > 그대로"* 와 같은 말이다. 직접 만들거나 재사용하면 업로드가 「이미 업로드」로 거부된다.

- **해결**: `PK\x03\x04`를 찾아 **그 지점부터 잘라 낸 뒤** zip으로 연다. 오프셋은 번들마다
  다를 수 있으니 상수로 박지 말고 찾는다.

  ```powershell
  Add-Type -AssemblyName System.IO.Compression.FileSystem
  $b = [System.IO.File]::ReadAllBytes($aitPath)
  $off = -1
  for ($i = 0; $i -lt 8192; $i++) {
    if ($b[$i] -eq 0x50 -and $b[$i+1] -eq 0x4b -and $b[$i+2] -eq 0x03 -and $b[$i+3] -eq 0x04) { $off = $i; break }
  }
  [System.IO.File]::WriteAllBytes($zipPath, $b[$off..($b.Length-1)])   # 스크래치패드로
  $z = [System.IO.Compression.ZipFile]::OpenRead($zipPath)
  ```

  ⚠️ **메모리 스트림으로 바로 열려다 한 번 더 막힌다** — `New-Object System.IO.Compression.ZipArchive`
  는 PowerShell 5.1에서 `Unable to find type [System.IO.Compression.ZipArchiveMode]`로 죽는다
  (`ZipFile`은 `...Compression.FileSystem`에 있지만 `ZipArchive`·`ZipArchiveMode`는
  `System.IO.Compression`에 있어 어셈블리를 하나 더 얹어야 한다). **임시 파일로 쓰고
  `ZipFile.OpenRead`를 쓰는 쪽이 짧다.**

  엔트리는 이렇게 생겼다 — 검사할 것은 `sources/assets/*.js`다.

  ```
  sources/assets\index-*.js · sources/assets\instructions-*.js · sources/assets\index-*.css · sources/index.html
  bundle.json · project-package.json     ← 개발 번들에만 붙었다
  ```

  읽기는 **UTF-8 명시 디코딩**으로 한다(`New-Object System.Text.UTF8Encoding($false)`) —
  안 그러면 CP949로 읽혀 한글 마커가 전부 어긋난다(글로벌 「Windows 셸 한글」 원칙).

- **재발방지**: **음성 대조군만으로 판정하지 않는다.** 이번에도 「개발용 입구 0건」 하나만
  봤으면 컨테이너를 못 열고 있다는 사실을 못 알아챘다. 검사는 항상 **셋**을 같이 낸다.

  | 종류 | 이번 번들에서 | 뜻 |
  |---|---|---|
  | 양성 — 이번에 넣은 것 | `하고 싶은 운동 직접 고르기` 등 `True` | 수정이 들어갔다 |
  | 양성 — 기존 기능 | `동작 보기`·`세트를 마치면 휴식 중에…` `True` | 회귀가 없다 · **계측기가 살아 있다** |
  | 음성 — 있으면 안 되는 것 | `온보딩 다시 보기` `False` | production이 맞다 |

  ⚠️ 마커는 **소스에 따옴표째 실린 리터럴**만 고른다. 이번에 `풀업바 필요`가 `False`로 나왔는데
  결함이 아니다 — 화면에서 `{EQUIPMENT_KO[k]} 필요`로 **런타임에 조립**되므로 번들에 그 문자열이
  통째로는 없다. 판별법은 하나다: **그 문구를 소스에서 그대로 찾을 수 있는가.**
