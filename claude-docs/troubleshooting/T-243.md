# T-243 · CRLF 작업 트리에서 `\n`을 품은 패턴은 무성으로 빗나간다

- **증상**: 한 세션에서 두 번 났고, 두 번 다 **에러가 아니라 조용한 오답**이었다.
  ① 돌연변이 스크립트가 `'          primeSound();\n'`을 못 찾아 「PATTERN NOT FOUND」 —
  같은 파일의 다른(한 줄짜리) 패턴은 멀쩡히 찾았다. ② `index.css`의
  `@media (prefers-reduced-motion: reduce) { ... }` 블록을 `/\{([\s\S]*?\n\})\s*\}/`로
  떠내려 했더니 `undefined` — 규약은 파일에 멀쩡히 있는데 테스트가 「없다」고 했다.

- **원인**: `.gitattributes`가 체크아웃을 CRLF로 정규화해서, 디스크의 줄바꿈은 `\r\n`이다.
  `'...;\n'`은 실제 바이트 `';\r\n'`과 안 맞고, `\n\}`는 `\r\n}`이나 들여쓴 `\r\n  }`와
  안 맞는다. **한 줄 안에서만 도는 패턴은 전부 통과하기 때문에** 도구가 고장 난 것으로 안
  보이고, 「그 코드가 없나 보다」로 읽힌다. 돌연변이 쪽은 더 나쁘다 — 변조가 안 걸린 것을
  「사살 못 함」이 아니라 **아예 시도 안 함**으로 넘어가, 검사한 적 없는 규칙이 검사한 것처럼
  집계된다.

- **해결**: 패턴에서 줄바꿈을 **뺐다.** 치환은 한 줄짜리 앵커로(`'primeSound();'`),
  블록 추출은 여는 줄에서 자르고 열 0의 `}`까지로(`css.split(/@media[^{]*reduce[^{]*\{/)[1]
  .split(/\n\}/)[0]` — `\n` 앞의 `\r`는 소비되므로 `\n\}`는 CRLF에서도 성립한다).

- **재발방지**: 이 레포에서 파일 내용을 문자열로 다루는 코드(테스트·스크립트)는 **패턴에
  `\n`을 넣지 않는다.** 여러 줄이 꼭 필요하면 `\r?\n`을 쓰거나, 읽은 뒤
  `.replace(/\r\n/g, '\n')`로 정규화하고 시작한다. 그리고 **찾기가 0건이면 실패로 취급한다** —
  돌연변이 스크립트가 「PATTERN NOT FOUND」를 눈에 띄게 찍은 덕에 잡혔다. 조용히 넘어갔다면
  변조 2종이 사살된 것으로 집계됐을 것이다(글로벌 「Windows 셸 원칙」의 무성 실패 계열).
