# 눈바디 사진 — 설계 (2026-08-28)

> Phase 7의 실기기 판정(토스 웹뷰 `getUserMedia` 라이브 프리뷰 — **성공**, PR #49)을 받아
> 본 기능을 설계한다. 요구는 한 문장이다: **"매일 운동하고 사진을 찍는다. 앱이 자세랑
> 카메라 위치를 지정해 준다 — 매일 똑같은 사진을 찍어서 몸의 변화를 확인하기 위해서."**
>
> 접근 방식은 **고스트 오버레이**로 합의됐다(자세 인식 AI 없음): 첫 촬영에서 기준 구도를
> 잡고, 이후에는 라이브 프리뷰 위에 기준 사진을 반투명으로 겹쳐 사용자가 스스로 몸을 맞춘다.

## 0. 요약 + 승인/선택이 필요한 결정

**v1 = 「기준 잡고 → 매일 같은 구도로 찍고 → 나란히 비교」의 최소한.** PR 셋으로 나간다:
① IndexedDB 사진 저장소 → ② 촬영 화면(프리뷰 + 고스트) → ③ 진입점 + 비교 화면.
사진은 기기를 떠나지 않는다(서버 0대 — 기존 기록과 같은 원칙).

사용자가 결정할 것:

| # | 결정 | 제안 | 대안 |
|---|---|---|---|
| 1 | **진입점** | 운동 완료 화면의 한 줄 제안 + 기록 탭의 눈바디 섹션(§3.1) | 홈 카드 / 넷째 탭 — 기각 이유는 본문 |
| 2 | **하루 1장** | 날짜가 키. 같은 날 다시 찍으면 교체(§5.2) | 하루 여러 장 — 비교 UI가 복잡해져 기각 |
| 3 | **카메라** | 전면 고정 + 3초 타이머. 후면·타이머 길이 선택은 ⏸ v2(§4.3) | 전/후면 토글을 v1에 — 고스트가 후면에선 무용지물이라 기각 |
| 4 | **고스트 원본** | **기준 사진(남아 있는 가장 오래된 것) 고정**(§4.2) | 직전 사진 — 누적 드리프트 위험으로 기각 |
| 5 | **보관 정책** | 긴 변 1280px · JPEG 0.8 · 상한 365장, 초과 시 오래된 것부터 삭제(§5.3) | 무제한 — 쿼터 초과가 「그날 사진 증발」로 나타나 기각 |
| 6 | **테스트 의존성** | `fake-indexeddb` devDependency 1개 추가(§7.1) | IDB 래퍼를 테스트 없이 — TDD 원칙 위반이라 기각 |
| 7 | **사용자 액션** | 콘솔 개인정보처리방침에 카메라·사진 문구가 필요한지 확인(§6.2). 다음 심사 릴리즈 노트에 카메라 사용 목적 명시 | — |

이 표만 승인하면 나머지는 구현 순서다.

## 1. 목표 / 비목표 (YAGNI)

**목표 (v1)**

- 첫 촬영: 격자 + 실루엣 가이드로 기준 구도를 잡는다
- 이후 촬영: 라이브 프리뷰 위에 기준 사진 고스트(반투명)를 겹쳐 같은 구도를 재현한다
- 저장: IndexedDB, 기기 로컬 전용. 하루 1장
- 비교: 기준 사진과 아무 날짜 사진을 **나란히** 본다. 장 단위 삭제 + 전체 삭제
- 기존 카메라 프로브 UI(`Settings.tsx`의 `CameraProbeSection`) 정리 — 본 기능이 대체한다

**비목표 (⏸ v2 이후 — 지금 안 하는 이유를 함께 적는다)**

- ⏸ **후면 카메라 · 타이머 길이 선택** — 후면은 화면을 못 보므로 고스트 정렬이 성립하지
  않는다. 거치대 + 후면 전신 촬영 수요가 실제로 오면 그때 (고스트 없는) 별도 모드로 판단
- ⏸ **두 장 슬라이더(오버레이 비교) · 타임랩스** — 나란히 두 장으로 「변화 확인」은 성립한다.
  타임랩스는 사진이 수십 장 쌓인 뒤에야 의미가 생기는 기능이라, 쌓이기 전에 만들면 빈 화면이다
- ⏸ **자세 인식·자동 정렬 AI** — 합의로 배제. 고스트가 그 역할을 사람 눈에 맡긴다
- ⏸ **사진 내보내기·공유** — 요구에 없다. 공유는 프라이버시 표면을 넓히는 쪽이라 요구가
  생겨도 신중히
- ⏸ **클라우드 백업** — 기존 기록과 같은 보류(plan.md). 「기기를 바꾸면 사라진다」를
  화면에 정직하게 적는 것으로 대신한다(기록 탭이 이미 그렇게 한다)
- ⏸ **체중·치수 입력 연동** — 별개 기능이다. 사진 옆에 숫자를 놓고 싶어지면 그때

## 2. 현황 실측 (설계가 딛는 사실)

코드를 직접 읽어 확인한 것들이다.

- **화면 라우팅은 `App.tsx`의 state 스위치다** — 라우터가 없다. `settings`(boolean)로
  전체화면을 여는 패턴이 이미 있고, 촬영 화면도 같은 패턴으로 얹는다. 탭은
  `home / shop / history` 셋이고 **탭을 늘리면 토스 탭바 가이드(T-222·T-224로 두 번
  반려)와 다시 부딪힐 표면이 늘어난다.**
- **저장은 전부 `storage.ts`의 localStorage** — 방어적 read(깨진 값은 빈 값으로) ·
  조용한 write(실패해도 화면은 돈다) · `Storage`를 인자로 받아 테스트가 주입한다.
  사진(Blob, 장당 ~150KB)은 localStorage(문자열, 통상 5MB 상한)에 못 담으므로
  IndexedDB가 필요하고, **이 파일의 세 관례(방어적 읽기·주입 가능·어휘 검증)를 그대로
  옮긴다**(§5).
- **`cameraProbe.ts`는 재사용 가능하다** — `probeCamera`(타임아웃 포함 getUserMedia) ·
  `stopStream`. 특히 「토스 웹뷰가 권한 프롬프트를 삼켜 영영 pending」 실패 모드에 대한
  타임아웃 처리와 「타임아웃 뒤 늦게 온 스트림은 트랙을 끈다」 정리가 본 기능에도 그대로
  필요하다. 제약이 `facingMode: 'user'` 고정인 것도 본 기능과 같다(§4.3).
- **프로브 UI는 `Settings.tsx`의 `CameraProbeSection`** — `DEV_TOOLS` 뒤라 릴리스
  번들에는 이미 없다. 본 기능이 들어가면 **컴포넌트째 삭제**한다(판정이 끝났고, 본
  기능의 촬영 화면이 같은 것을 더 잘 잰다).
- **완료 화면(`Workout.tsx`의 `s.finished` 분기)이 「운동 직후」의 유일한 자리다** —
  이미 체감 1문항이 있고, 저장 버튼(`save`)이 `onFinish`로 App에 돌아간다. 여기에
  눈바디 제안을 얹는 것이 「매일 운동하고 찍는다」와 정확히 겹친다.
- **테스트 관례**: vitest + 파일 머리 `// @vitest-environment jsdom`(전역 금지 —
  T-229), 돌연변이 실측으로 판별력 확인, `todayKey()`가 KST `YYYY-MM-DD`를 준다 —
  사진 키로 그대로 쓴다.
- **`apps-in-toss.config.ts`에 `camera` 권한이 이미 선언돼 있다.** 주석이 「프로브
  실패 시 걷는다」인데 성공했으므로 **주석만 본 기능 근거로 고쳐 단다.**

## 3. 진입점 — 어디서 찍고 어디서 보나

### 3.1 결정: 완료 화면 제안 + 기록 탭 섹션

| 대안 | 판정 | 이유 |
|---|---|---|
| **A. 운동 완료 화면에 한 줄 제안** | ✅ 채택(촬영 진입) | 요구 문장이 「매일 **운동하고** 찍는다」다. 완료 화면은 그 순간 그 자체이고, 체감 1문항처럼 **선택 사항으로 얹는 자리**가 이미 있다 |
| **B. 기록 탭에 눈바디 섹션** | ✅ 채택(집) | 비교·회고·삭제는 「기록」의 성격이다. 운동 안 한 날에도 찍을 수 있는 유일한 입구가 되고, 「기록은 이 기기에만 저장됩니다」 문구도 이미 그 화면에 있다 |
| C. 홈 카드 | ❌ | 홈의 일은 「오늘 운동 시작」 하나다. 카드를 얹으면 시작 CTA와 경쟁하고, 이탈은 광고 슬롯 소멸이다(plan.md의 상시 주의와 같은 논리) |
| D. 넷째 탭 | ❌ | 탭바는 두 번 반려된 표면이다(T-222·T-224). 매일 1번 여는 기능에 탭 하나는 과하고, 3탭 캡슐의 검증된 형태를 흔든다 |

구체적으로:

- **완료 화면**: 「기록 저장하고 끝내기」(primary) 위에 ghost 버튼 한 줄 —
  「📷 오늘의 눈바디 남기기」. 누르면 **기록 저장을 먼저 끝내고**(기존 `save()` 그대로)
  촬영 화면을 연다. 사진 때문에 운동 기록 저장이 뒤로 밀리는 경로를 만들지 않는다 —
  기록은 광고보다 귀하고, 사진보다도 귀하다.
- **기록 탭**: 기록 리스트 **위**에 눈바디 카드 한 장 — 최근 사진 썸네일(없으면 빈 상태
  문구) + 「오늘 찍기 / 오늘 다시 찍기」 버튼 + 「비교」 진입. 삭제는 비교 화면에서 한다(§4.4).

### 3.2 App.tsx 배선

`settings`와 같은 boolean state 하나(`bodyPhoto`)로 전체화면을 연다. 완료 화면 경로는
`onFinish` 뒤에 여는 순서만 지키면 된다(세션 종료 → 촬영). 라우터·컨텍스트 도입은 없다.

## 4. 촬영 화면 UX

### 4.1 플로우

```
[진입] → 카메라 켜는 중 → 프리뷰
                │ (실패: unsupported / NotAllowedError / timeout → 원문 + 안내, §4.5)
                ▼
   사진 0장?  ──예──▶ 첫 촬영 모드: 격자 + 실루엣 가이드 + 안내 한 줄
      │아니오              "이 구도가 기준이 됩니다. 벽·조명·거리를 기억해 두세요"
      ▼
   고스트 모드: 격자 + 기준 사진(opacity 0.4) 오버레이 + 고스트 켬/끔 토글
      ▼
   [촬영] 또는 [3초 후 촬영] → 카운트다운 → 캡처
      ▼
   확인 화면: 방금 찍은 사진 + [저장] / [다시 찍기]
      ▼
   저장(같은 날짜면 교체) → 촬영 화면 닫힘 → 진입했던 화면으로
```

- **격자**: 3×3 선(CSS `linear-gradient` 또는 절대배치 div 4개 — 라이브러리 없음).
  격자는 첫 촬영에도 이후에도 항상 그린다 — 수평·중앙 맞추기의 최소 도구다.
- **실루엣**: 전신 외곽 path 하나짜리 인라인 SVG(반투명 선). 정밀할 필요가 없다 —
  「화면 세로를 몸으로 채우고 중앙에 서라」를 말하는 그림이면 족하다. 사진이 1장이라도
  생기면 실루엣은 안 그린다(고스트가 그 일을 더 잘한다).
- **고스트 투명도는 0.4 고정 + 켬/끔 토글.** 슬라이더는 안 만든다 — 정렬하는 동안 잠깐
  끄고 싶은 요구(내 몸이 안 보인다)는 토글로 충분하고, 값 조절은 저장할 상태만 늘린다.

### 4.2 고스트 원본 — 기준 사진 고정 (직전 사진이 아니라)

| 대안 | 판정 | 이유 |
|---|---|---|
| **기준 사진(남아 있는 가장 오래된 것)** | ✅ | 매일 직전 사진에 맞추면 **하루 1~2px의 어긋남이 누적**돼 한 달 뒤 구도가 처음과 딴판이 된다(복사기의 복사본을 다시 복사하는 문제). 기준 고정이면 어긋남이 누적되지 않는다 |
| 직전 사진 | ❌ | 몸이 변한 만큼 맞추기 쉽다는 장점은 있으나, 고스트로 맞추는 것은 **몸이 아니라 구도**(벽·프레임·발 위치)다. 구도 기준은 변하지 않는 쪽이 맞다 |
| 기준을 사용자가 지정 | ⏸ v2 | 상태(기준 날짜)와 UI가 하나씩 는다. v1에서는 **삭제가 곧 기준 변경이다** — 첫 사진이 마음에 안 들면 지우면 다음으로 오래된 사진이 기준이 된다. 별도 상태가 0개 |

### 4.3 카메라 방향과 셀프 촬영 현실

- **전면 고정.** 고스트 정렬은 **프리뷰를 보면서** 해야 성립하는 UX다 — 후면으로 돌리는
  순간 화면이 안 보여 고스트가 무용지물이다. `cameraProbe.ts`의 `facingMode: 'user'`
  판단을 그대로 승계한다. 실기기 검증(PR #49)도 이 방향으로 했다.
- **거치 전제 + 3초 타이머.** 전면 팔뻗기 셀피로는 상반신까지만 나온다. 전신을 원하면
  폰을 어딘가 기대 세우고 물러서야 하는데, 그러면 촬영 버튼에 손이 안 닿는다 — 그래서
  타이머가 장식이 아니라 **전신 촬영의 유일한 경로**다. 버튼은 둘: 「촬영」(즉시)과
  「3초 후 촬영」(카운트다운 큰 숫자 표시). 길이 선택(3/5/10초)은 요구가 생기면 v2.
- **미러 일관성 (함정).** 전면 프리뷰는 거울처럼 좌우 반전(`scaleX(-1)`)으로 보여주는
  것이 자연스럽다. 그러면 **저장본도 같은 방향으로 반전해 저장해야 한다** — 프리뷰는
  거울상인데 저장본(과 그것으로 만든 고스트)이 정방향이면, 다음 촬영에서 고스트와 내
  몸이 좌우로 어긋나 영영 안 맞는다. 캔버스 캡처 시 같은 변환을 적용한다. 이 일관성이
  테스트 대상이다(§7.2).

### 4.4 비교 화면 (v1 최소)

- **나란히 두 장**: 왼쪽 = 기준(가장 오래된), 오른쪽 = 선택한 날짜(기본 최신).
  각각 아래에 날짜. 오른쪽만 ‹ › 로 날짜를 넘긴다 — 왼쪽까지 넘기게 하면 「무엇 대비
  무엇인가」가 흐려진다.
- **삭제는 여기서**: 오른쪽 사진에 「이 사진 삭제」(장 단위) + 화면 맨 아래 「사진 모두
  삭제」(`window.confirm` 한 번 — 커스텀 다이얼로그는 안 만든다). 프라이버시 기능이라
  v1에서 뺄 수 없다.
- 사진이 1장이면 비교가 성립하지 않는다 — 그 장 하나와 「내일 또 찍으면 비교할 수
  있어요」 문구.

### 4.5 실패 경로

프로브가 감별해 둔 세 갈래를 사용자 문구로 옮긴다(원문은 작은 글씨로 병기 — 문의 대응용):

- `unsupported` → "이 환경에서는 카메라를 쓸 수 없어요"
- `NotAllowedError` → "카메라 권한이 꺼져 있어요. 토스 앱 설정에서 허용해 주세요"
- `timeout` / 그 외 → "카메라를 여는 데 실패했어요. 잠시 후 다시 시도해 주세요"

어느 경로든 **닫기 버튼으로 멀쩡히 돌아간다.** 심사자가 권한을 거부하고 눌러 볼 것을
전제한다(§6.1).

### 4.6 스트림·URL 수명

- 스트림 정리는 프로브의 관례 그대로 — effect cleanup 한 곳에서 `stopStream`. 촬영
  화면을 닫으면(언마운트) 카메라가 반드시 꺼진다.
- 고스트·썸네일·비교는 `URL.createObjectURL(blob)`을 쓴다 — **만든 곳이 revoke까지
  책임진다**(effect cleanup). 안 지키면 사진을 넘길 때마다 blob URL이 새고, 조용히
  메모리만 자란다.

## 5. 데이터 모델 · 용량 정책

### 5.1 왜 IndexedDB인가 (기존 패턴과의 접점)

localStorage는 문자열 전용에 통상 5MB — 사진 30장이면 끝난다. IndexedDB는 Blob을
그대로 담고 쿼터가 수백 MB 단위다. 다만 API가 비동기·이벤트 기반이라 `storage.ts`에
섞지 않고 **`photoStore.ts`를 따로 둔다.** 옮겨 가는 것은 API가 아니라 관례다:

- **방어적 읽기** — DB가 안 열리면(프라이빗 모드 등) 빈 목록으로 시작하고 화면은 돈다
- **주입 가능** — `indexedDB`(IDBFactory)를 인자로 받는다. 테스트가 fake를 넣는다
- **조용한 실패의 예외 하나**: 기존 `write`는 실패를 삼키지만 **사진 저장 실패는
  삼키면 안 된다** — 방금 찍은 사진이 소리 없이 증발하면 사용자는 한 달 뒤에야 안다.
  저장 결과를 boolean으로 돌려주고, 실패 시 확인 화면에 "저장하지 못했어요"를 띄운다.

### 5.2 스키마

```ts
// DB 'restfit-photos' v1 · object store 'photos' · keyPath 'date'
type BodyPhoto = {
  date: string;      // todayKey() — 'YYYY-MM-DD'. 키이자 「하루 1장」의 구현
  blob: Blob;        // image/jpeg
  capturedAt: number; // Date.now() — 같은 날 재촬영 판별·정렬 부차 정보
  width: number;     // 저장본 픽셀 크기. 비교 화면 레이아웃이 로드 전에 자리를 잡는 데 쓴다
  height: number;
};
```

- **키 = 날짜.** `put`이면 같은 날 재촬영이 자동으로 교체다 — 「하루 1장」에 코드가 0줄
  든다. 운동 기록의 `date` 키(`todayKey`)와 같은 시간대 규약을 쓴다(KST — UTC로 자르면
  아침 사진이 어제로 찍힌다, `storage.ts` 주석과 같은 함정).
- 메타를 localStorage에 따로 두지 않는다 — 두 저장소에 같은 사실을 두면 어긋나는 날이
  온다(자동 메모리 인덱스와 같은 교훈). 목록·기준·최신 전부 IDB 한 곳에서 읽는다.

### 5.3 해상도 · 압축 · 상한

- **긴 변 1280px로 다운스케일, JPEG 품질 0.8** — 장당 대략 100~200KB. 폰 화면 비교
  용도로 충분하고(비교 화면의 반쪽 폭은 ~180px), 원본 해상도(4K급)를 담으면 장당 수 MB로
  쿼터를 30배 빨리 태운다.
- **상한 365장.** 넘으면 저장 시 가장 오래된 것부터 지운다. 1년 치 ≈ **최대 70MB** —
  IDB 쿼터(통상 디스크 비례, 수백 MB+)에 여유 있다. 1년 넘게 찍은 사람의 기준 사진이
  이때 밀려나는데, **1년 전 몸은 이미 기준이 아니다** — 자연스러운 기준 갱신으로 수용한다.
  ⚠️ 토스 웹뷰의 실제 쿼터는 미실측이다(§9) — 그래서 초과(QuotaExceededError) 시에도
  "공간이 부족해요 — 오래된 사진을 지워 주세요" 안내가 v1에 있어야 한다.

### 5.4 photoStore API (전부 async)

```ts
openPhotoDb(idb?: IDBFactory): Promise<PhotoDb | null>  // null = 못 씀(화면이 안내)
savePhoto(db, photo): Promise<boolean>                  // 상한 프루닝 포함. false = 저장 실패
listPhotos(db): Promise<BodyPhoto[]>                    // date 오름차순 — [0]이 기준
deletePhoto(db, date): Promise<void>
clearPhotos(db): Promise<void>
```

목록이 커야 400개 미만 메타이므로 인덱스·커서 최적화는 안 한다 — `getAll`이면 된다.

## 6. 심사 리스크 (토스 검수 관점)

세 번의 심사 왕복(T-222·T-224)에서 배운 것: 반려는 기능이 아니라 **가이드가 명시한
표면**에서 난다. 이번 기능이 새로 여는 표면은 카메라와 신체 사진이다.

### 6.1 카메라 사용 목적 고지

- `camera` 권한은 이미 선언·검수 통과 상태다(프로브 번들이 심사를 지나왔다). 다만 이제
  **사용자 눈에 보이는 카메라 기능**이 처음 실리므로, 심사자가 목적을 물을 표면이 생긴다.
- **촬영 화면 첫 진입 시(그리고 화면 안에 상시) 한 줄 고지**: "사진은 이 기기에만
  저장되며 어디로도 전송되지 않습니다." — 사실이고(서버 0대), 검수·사용자 양쪽에
  같은 문장으로 답한다.
- **릴리즈 노트에 카메라 사용 목적을 적는다**: "눈바디 기록 — 카메라는 몸 변화 기록
  사진 촬영에만 쓰이며 사진은 기기에만 저장됩니다." 심사자가 권한의 근거를 릴리즈
  노트에서 먼저 찾는다.
- **권한 거부 상태에서 앱이 멀쩡해야 한다**(§4.5) — 심사자는 거부부터 눌러 본다.

### 6.2 프라이버시 문구 (사용자 액션)

- 콘솔의 개인정보처리방침이 카메라·사진을 다루는지 확인이 필요하다
  (`miniapp_update_privacy_policy` 경로). **로컬 저장 전용이라 「수집」이 아닐 가능성이
  높지만, 판단은 문구를 보고 한다** — 이 확인은 사용자(콘솔 접근)와 함께 다음 심사 전에
  1회. 기록 탭의 "이 기기에만 저장됩니다" 문구를 눈바디 카드에도 붙인다.

### 6.3 신체 사진과 19+

- 앱이 `minAge: 19`다(T-221 — 우리가 못 바꾼다). 성인 전용이라 신체 사진 기능 자체의
  연령 리스크는 없다.
- ⚠️ **스토어 스크린샷에 실제 신체 사진을 쓰지 않는다.** 눈바디 화면을 스크린샷에
  실으려면 실루엣·목업으로 찍는다 — 속옷 차림 사진이 스토어에 실리면 그게 새 반려
  사유가 된다. plan.md의 관례대로, **이 기능의 화면이 라이브에 실릴 때 스토어 스크린샷
  교체 여부를 같이 본다**(이번엔 기존 4장에 눈바디가 없으므로 v1 출시만으로는 교체
  불필요 — 스크린샷에 싣고 싶을 때만).
- 촬영 유도 문구는 건조하게 유지한다("같은 구도로 찍어요") — 노출을 유도하는 문구는
  만들지 않는다.

## 9. 리스크 · 미검증 가정

- **토스 웹뷰의 IndexedDB 영속성·쿼터가 미실측이다.** 성립 안 하면(웹뷰 재시작마다
  증발 등) 기능의 저장 축이 무너진다 — 그래서 **PR A를 먼저 실기기에서 스모크**해 볼
  수 있게 순서를 짰다(저장소가 화면 없이도 dev 도구 한 줄로 확인 가능). 실패로 판정되면
  파일 다운로드 방식 등 차선을 그때 설계한다 — 지금 대비하지 않는다(YAGNI).
- **전면 카메라의 실해상도**를 모른다 — 1280 다운스케일이라 상한만 맞으면 되지만,
  극단적으로 낮으면(480p) 비교 가치가 깎인다. 실기기 검증 항목이다.
- **`toBlob`의 JPEG 인코딩이 웹뷰에서 되는가** — 표준이라 될 것이나, 안 되면 `toDataURL`
