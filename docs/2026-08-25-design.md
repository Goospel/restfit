## 1. 무엇을 만드는가

**집에 있는 기구로 할 수 있는 홈트 루틴을 짜주고, 세트 사이 휴식 시간에 광고를 재생하는** 미니앱.

**수익 구조 — 둘로 갈린다**

| | 언제 | 특징 |
|---|---|---|
| **전면 광고** | 매 휴식 | **주 수익.** 세션당 여러 번 반복 |
| **쉐어링크** | 기구 해금 시 | 보조. 드물지만 객단가가 크다 |

---

## 2. 왜 이게 되는가

### 광고의 마찰이 0이다

보통 리워드 광고는 *"보상을 받으려면 30초 참으세요"* 다. 사용자에게 기다림은 손해다.
**운동 중 휴식은 어차피 기다려야 하는 시간이다.** 60초를 타이머만 보느니 광고를 보는 편이 덜 지루하다.

광고를 **"참는 것"에서 "시간 때우는 것"으로** 바꾼다. 광고와 사용자 이익이 충돌하지 않는 드문 구조다.

### 노출 밀도가 비정상적으로 높다

한 세션에 12세트면 **광고 슬롯이 12개**다. 보통 앱은 세션당 1~2회가 한계다.

### 경쟁사가 구조적으로 못 한다

이게 핵심이다. 이 프로젝트에서 [판정 기준 ②](ideas.md)를 통과한 **첫 번째 차별점**이다.

- **Fitbod**(월 $15.99), **플랜핏**(프리미엄) — 둘 다 **구독 모델**이다
- 구독자에게 운동 중 광고를 12번 트는 건 브랜드 자살이고, 무료 티어에 넣어도 프리미엄 전환 서사와 엉킨다
- **기술적으로 못 하는 게 아니라 수익 모델이 충돌해서 못 하는 자리**다

앱인토스 검색으로도 **휴식 시간에 광고를 트는 앱은 없음**을 확인했다(2026-08-25).

### 리텐션 문제를 수익 모델로 우회한다

운동 앱의 고질병은 리텐션이다(40~50%가 3개월 내 이탈). **구독은 이탈하면 0이지만 광고는 쓰는 동안 뽑는다.** 레드오션의 약점이 이 모델에서는 덜 아프다.

## 3. 규율 — 이게 곧 수익 구조다

> **광고가 휴식보다 길거나 운동 중에 끼어들면 사용자가 이탈하고, 그러면 세션당 12회라는 노출 밀도 자체가 사라진다.**

이 아이디어가 돈이 되는 이유가 "어차피 버리는 시간에 들어가서"이므로, **그 선을 넘는 순간 근거가 무너진다.** 규율이 곧 제품이다.

**휴식 길이는 운동이 정한다. 광고는 그 안에서 돈다.**

| 운동 유형 | 휴식 | 광고 |
|---|---|---|
| 고중량 저반복 | 120~180초 | 재생 후 남은 시간 카운트다운 |
| 근비대 | 60~90초 | 재생 후 남은 시간 카운트다운 |
| 서킷·유산소 | 15~30초 | **재생하지 않는다** |

절대 하지 않는 것:
- 광고가 끝나야 휴식이 끝나는 구조 (운동이 광고에 종속된다)
- 운동 세트 **중** 광고·상품 노출
- 휴식보다 긴 광고

## 4. 확정된 제약

### 앱인토스

- **미니앱 스택에 선택지가 없다**: Vite + React **18** + `@apps-in-toss/web-framework` + `@toss/tds-mobile`
  - ⚠️ React 19 불가 — TDS 2.5.1의 peer가 `^16.8.3 || ^17 || ^18`
- 배포: `npm run build` → `npx ait build` → `npx ait deploy`. `.ait` 번들을 토스 인프라가 호스팅
- 정적 SPA. 서버 렌더링 없음

### 광고 API — load와 show가 분리돼 있다

```ts
loadFullScreenAd({ options, onEvent, onError })   // 미리 불러두기
showFullScreenAd({ options, onEvent, onError })   // 그때 노출
TossAds.attachBanner(...)                          // 인라인 배너
GoogleAdMob.{load,show,is}AppsInTossAdMob(...)     // AdMob 경유
```

**이 분리가 이 아이디어를 성립시킨다.** 세트를 하는 **동안** 다음 휴식용 광고를 preload 하고, 휴식이 시작되면 즉시 노출한다. 로딩 대기가 0이라 운동 흐름이 안 끊긴다.

광고 그룹 ID는 앱인토스 콘솔에서 발급한다(BookTimer가 `VITE_REWARD_AD_GROUP_ID` 등으로 이미 사용 중).

### 쉐어링크

| 제약 | 영향 |
|---|---|
| 키워드 검색 API 없음 | 기구 상품은 카테고리 베스트에서 **수동 선별** |
| 링크 발급 10,000건/일, 기존 링크 재요청은 차감 X | 기구 11종 × 3~5개 = **50개 남짓.** 한도가 문제되지 않는다 |
| 출발지 IP 화이트리스트 | **발급 스크립트를 돌릴 때만** 필요. 런타임엔 불필요 |
| 어트리뷰션 24시간 × 전 카테고리 | 추천 기구를 안 사도 그날 산 것이면 인정 |
| 브랜드에 "토스" 사용 금지 | 미니앱 이름·로고에 불가 |
| 대가성 문구 필수 | 쉐어링크가 노출되는 화면에 고정 표시 |
| 조회 API의 `productUrl`은 추적 안 됨 | 반드시 발급 API의 `shortUrl` |

⚠️ **미니앱에서 쉐어링크를 열면 앱 복귀가 불안정하다**는 제보가 있다(토스 "개선 논의 중"). [Phase 0.5](#10-최우선-검증-phase-05)에서 실측한다.

## 5. 아키텍처 — 서버 0대

```
[토스 앱]
  └─ 미니앱 (Vite + React 18 + TDS)   ← .ait 번들, 토스 인프라가 호스팅
        ├─ 운동 데이터 873개   → 번들에 정적 포함
        ├─ 보유 기구 · 기록    → localStorage
        └─ 기구 쉐어링크 50개  → 번들에 정적 포함
```

**서버도 DB도 EC2도 없다.** 쉐어링크 발급 스크립트만 가끔 로컬에서 돌려 JSON을 갱신하고 커밋한다(그때만 IP 등록이 필요하다).

> ⚠️ `ponytail:` 기록이 localStorage에만 있어 기기를 바꾸면 날아간다. 사용자가 요구하면 토스 로그인 + 서버로 올린다. 지금은 넣지 않는다.

## 6. 운동 데이터

[free-exercise-db](https://github.com/yuhonas/free-exercise-db) — 873개, **Unlicense(퍼블릭 도메인)**, 이미지 포함.

**2026-08-25 실측 — 해금 수치**

```
맨몸만        111개
+ 덤벨        234개  (+123, 2.1배)   ← 단일 최대 해금
+ 케틀벨       307개  (+53)
+ 밴드        254개  (+20)
```

→ 첫 구매 추천은 **덤벨**. 해금량이 압도적이고 토스쇼핑의 소액 단품 강세와도 맞는다.

**정제 과제**

1. `equipment: null` 77개는 대부분 맨몸 스트레칭 → 맨몸에 합치면 111→188개가 되고 덤벨 배수가 2.1→1.24배로 떨어진다. **`category`로 근력/스트레칭을 분리해야 훅이 산다**
2. `other` 122개가 잡동사니 — Ab Roller(홈트 가능) / Atlas Stones(스트롱맨) / Battling Ropes(짐 전용) 수동 재분류
3. 밴드가 20개뿐이라 해금 효과가 초라해 보인다
4. 영어 → 한글화 1회 배치 (운동명·부위·instructions)

**장비 어휘(홈트 기준)**: 맨몸 · 덤벨 · 밴드 · 케틀벨 · 풀업바 · 벤치 · 짐볼 · 폼롤러 · 메디신볼 · 복근롤러 · 바벨
케이블·머신·스미스는 **헬스장 전용이라 숨긴다**(홈트 앱에서 노이즈).

## 7. 로직 — 순수 함수가 전부 (TDD 대상)

```ts
filterByEquipment(exercises, owned)            // 보유 기구로 필터
unlockGain(exercises, owned, candidate)        // "덤벨 추가하면 +123개"  ← 쉐어링크의 근거
pickRoutine(exercises, owned, history, seed)   // 부위 로테이션 + 균형 + 난이도
adPlan(restSeconds, adState)                   // ★ 광고를 틀지·언제 틀지  ← 신규, 핵심
```

`pickRoutine`의 seed는 **날짜**다. 같은 날 재접속해도 루틴이 안 바뀐다. 규칙 기반이라 **LLM은 쓰지 않는다.**

### `adPlan` — 이 앱의 심장

입력: 이번 휴식 길이, 오늘 이미 노출한 횟수, 직전 광고 결과(성공/실패/미충전)
출력: `{ show: boolean, reason }`

규칙:
- 휴식 < 40초 → 안 튼다 (§3 규율)
- 직전 요청이 미충전이면 다음 슬롯은 건너뛴다 (연속 실패 시 백오프)
- frequency cap에 걸리면 남은 세션은 타이머만 (사용자에게 광고 실패를 보이지 않는다)

**광고를 못 틀어도 앱은 정상 동작해야 한다.** 광고는 수익이지 기능이 아니다.

| 기록 | 직전 기록 자동 표시 (*"지난번 20kg × 10"*) |

## 9. 광고 통합 상세

```
세트 시작 ─────────────────────────┐
   │                               │ 이 사이에 다음 광고 preload
   ▼                               │
세트 완료 → 휴식 시작 ◀────────────┘
   │
   ├─ adPlan이 show=true → showFullScreenAd
   │     └─ 광고 종료 → 남은 휴식 카운트다운
   └─ show=false → 타이머만
```

- **preload는 세트를 하는 동안**. 휴식이 시작된 뒤 로드하면 대기가 생긴다
- 광고 실패·미충전은 **조용히 넘어간다**. 에러를 사용자에게 보이지 않는다
- 광고 재생 중에도 **휴식 타이머는 계속 흐른다**. 광고가 시간을 늘리지 않는다

## 10. 최우선 검증 (Phase 0.5)

**한 번의 실기기 테스트로 둘을 잰다.** 이미 만들어둔 검증 앱에 얹는다.

### ① 광고를 세션당 몇 번 틀 수 있는가 ★

이 아이템의 **수익 전체가 이 가정 위에 있다.** 5회에서 막히면 모델이 절반 이하로 줄어든다.

- 60초 간격으로 12회 연속 요청
- 몇 번째에서 실패하는지, 어떤 에러인지, 채워지는 비율을 기록
- ⚠️ **앱인토스 광고 정책에 노출 빈도 제한이 있는지도 같이 확인한다.** 정책상 막히면 실측 이전에 끝이다

### ② 미니앱에서 쉐어링크 복귀가 되는가

수동 발급한 쉐어링크로 `Device.openURL` / 구 `openURL` 둘 다 시험. 판정 기준은 `miniapp/README.md`.

로그는 localStorage에 남겨 앱이 재시작돼도 증거가 살아남는다.

## 11. 리스크

| 리스크 | 대응 |
|---|---|
| **광고 fill rate·frequency cap** | §10-① 실측. 낮으면 슬롯 수를 줄이고 배너 병행을 검토 |
| **앱인토스 광고 정책 제한** | §10과 함께 확인. 정책이 막으면 아이템 재검토 |
| 쉐어링크 복귀 실패 | 보조 수익이라 **치명적이지 않다.** 실패하면 광고 단독으로 간다 |
| 경쟁사가 따라 함 | 구독 모델이라 못 따라온다(§2). 다만 신생 무료 앱은 따라올 수 있다 |
| 운동 데이터 정제 부담 | 873개 수동 분류 + 번역. 1회 비용 |
| 리텐션 | 광고 모델이라 덜 아프지만, 낮으면 세션 수 자체가 준다 |
