# 토스쇼핑 가격 이력 검증 서비스 — 설계

작성 2026-08-25 · **같은 날 개정: 웹사이트 → 앱인토스 미니앱 단독**
아이템 선정 경위와 접은 안들은 [ideas.md](ideas.md)

> **개정 사유**: 초판은 검색 유입을 노리는 웹사이트를 전제했다. 실행 환경이 앱인토스 미니앱으로 확정되면서
> SEO 관련 설계(사이트맵·구조화 데이터·URL 슬러그·상품별 페이지 롱테일 전략·Next.js 서버 모드)가 **전부 무효**가 됐다.
> 미니앱은 검색엔진에 색인되지 않는다. 트래픽은 토스 앱 내 노출에서 온다.

---

## 1. 무엇을 만드는가

토스쇼핑 상품의 **가격 이력을 매일 쌓아, 지금의 할인이 진짜인지 판정**해주는 토스 미니앱.

```
"할인율 40%라는데, 이 상품 지난 60일 평균가가 오늘 가격보다 쌌습니다."
```

**수익**: 토스쇼핑 쉐어링크 어필리에이트 10%. 상품 화면의 "토스쇼핑에서 보기"가 쉐어링크다.

### 왜 이게 되는가 — 구조적 해자

**커머스 사업자는 자기 셀러의 할인이 가짜라고 표시할 수 없다.** 못 하는 게 아니라 구조적으로 안 하는 것이라 영구적이다.

경쟁: 다나와·에누리·특가요정은 전부 쿠팡 중심이고, 쉐어링크 Open API는 이제 막 열렸다(시범운영). 그리고 **토스쇼핑은 오픈마켓이라 중소 셀러 상품이 다나와에 없다.** 정면 승부가 아니라 빈 자리를 먹는다.

**시장**: 토스쇼핑 MAU 약 900만 · GMV 전년 대비 +80%. 토스 유저는 결제수단이 이미 등록돼 있어 구매 마찰이 거의 0이다.

## 2. ⚠️ 최우선 검증 — 이게 실패하면 전부 무의미하다

> **미니앱에서 쉐어링크를 열면 토스 앱으로 정상 복귀하는가?**

[앱인토스 개발자 커뮤니티](https://techchat-apps-in-toss.toss.im/t/toss-im/4625)에 `openURL()`로 토스쇼핑 쉐어링크를 열면 **앱 복귀가 불안정하고 세션이 꼬인다**는 제보가 있다. 토스 답변은 *"내부 개선 논의 중"*(미해결). 제보자는 결국 **토스쇼핑 링크를 빼고 쿠팡 링크만 쓰고 있다.**

**우리 수익 전부가 그 링크 하나에 달려 있다.** 문서로는 결론이 안 난다.

**검증 방법 — Open API 승인 없이 지금 가능하다**

1. 토스쇼핑 앱에서 아무 상품이나 공유 아이콘 → "쉐어링크 공유하기"로 **수동 발급**
2. 최소 미니앱(화면 1개 · 버튼 1개)에서 그 링크를 `openURL()`로 연다
3. 실기기에서 복귀·세션 유지를 확인한다

이 스캐폴드는 본 프로젝트의 시작점이라 **버리는 코드가 아니다.** 나머지 설계는 이 검증 통과를 전제로 한다.

**실패 시**: 어필리에이트 수익 모델이 성립하지 않는다. 앱인토스 리워드 광고로 수익원을 바꾸거나(BookTimer가 쓰는 방식), 웹사이트 채널을 되살리는 것을 재검토한다.

## 3. 확정된 제약

### 쉐어링크 Open API

| 제약 | 설계에 미치는 영향 |
|---|---|
| **키워드 검색 API 없음** | 카탈로그 진입점이 랭킹·특가·카테고리뿐. 내가 긁어 만든 인덱스가 곧 해자 |
| **조회 10,000상품/일** (중복도 차감) | *매일 추적 가능한 상품 수 ≤ 10,000.* 수집기 설계 전체를 규정 |
| **링크 발급 10,000건/일** (기존 링크 재요청은 차감 X) | 링크는 DB에 캐싱해 영구 재사용 |
| 10 rps, 버스트 30 | 순차 호출로 충분. 백오프 필요 |
| **출발지 IP 화이트리스트** | EC2 + Elastic IP 필수. 가정용 유동 IP는 조용히 깨진다 |
| 어트리뷰션 24시간 × 전 카테고리 | 추천 상품을 안 사도 그날 산 것이면 인정 |
| **브랜드에 "토스" 사용 금지** | 미니앱 이름·로고에 토스 불가 |
| 대가성 문구 필수 | 쉐어링크가 노출되는 모든 화면에 고정 표시 |
| 조회 API의 `productUrl`은 추적 안 됨 | 반드시 발급 API의 `shortUrl`을 쓴다 |
| 수수료 10%는 이벤트 요율 | 코드에 하드코딩하지 않는다 |

### 앱인토스

- **미니앱 스택에 선택지가 없다**: Vite + React **18** + `@apps-in-toss/web-framework` + `@toss/tds-mobile`
  - ⚠️ React 19 불가 — TDS 2.5.1의 peer가 `^16.8.3 || ^17 || ^18`
- 배포: `npm run build` → `npx ait build` → `npx ait deploy`. 산출물은 `.ait` 번들, 토스 인프라가 호스팅
- 정적 SPA다. **서버 렌더링이 없다** → 데이터는 별도 API 서버에서 가져온다
- **외부 링크 정책은 우리에게 유리하다.** 허용 예시에 이게 명시돼 있다:
  > *"각 제품을 소개·추천한 뒤 최저가 구매 플랫폼으로 이동"*

  제한되는 건 *"주요 기능·흐름이 외부 링크에 의존하는 구조"*다. 우리는 가격 이력과 판정이 미니앱 안에서 완결되고 링크는 그다음이라 통과 쪽에 가깝다.
- 어뷰징 정책: 같은 워크스페이스에서 **같은 기능의 미니앱 반복 출시 금지**. BookTimer와 기능이 달라 무관하다

## 4. 아키텍처

```
[토스 앱]
  └─ 미니앱 (Vite + React 18 + TDS)      ← .ait 번들, 토스 인프라가 호스팅
        │  HTTPS  /api/**
        ▼
  [EC2 t4g.medium + Elastic IP]
    ├─ Spring Boot        읽기 전용 API
    ├─ PostgreSQL         같은 인스턴스에 직접 설치
    └─ @Scheduled         일 1회 수집 (고정 IP가 필요한 유일한 이유)
```

**EC2는 정적 파일을 서빙하지 않는다.** 미니앱은 토스가 호스팅하므로 EC2는 순수 API 서버 + 배치다. nginx는 API 앞단의 TLS 종단·리버스 프록시로만 쓴다.

**선택 근거**

- **Spring Boot**: BookTimer로 검증된 Spring + 미니앱 패턴을 재사용한다. 익숙함이 주는 속도가 가장 크다
- **수집기는 별도 프로세스가 아니라 `@Scheduled`**: 하루 1번 몇 분짜리 작업에 별도 배포·cron 관리를 늘릴 이유가 없다. Spring Batch는 이 규모에 과하다
- **Postgres는 RDS가 아니라 EC2에 직접 설치**: 추가 비용 0. 백업은 `pg_dump` 일 1회. 운영 부담이 커지면 그때 RDS로 옮긴다
- **t4g.medium(4GB)**: JVM + Postgres를 같이 돌려야 한다. t4g.small(2GB)은 빠듯하다
- **로그인 없음**: 회원 개념이 없는 공개 읽기 전용 데이터다. 토스 로그인도 쓰지 않는다

## 5. 데이터 모델 (PostgreSQL)

```sql
CREATE TABLE products (
  taca_item_id  BIGINT PRIMARY KEY,
  display_name  TEXT   NOT NULL,
  thumbnail_url TEXT,
  category_ids  BIGINT[],
  first_seen_on DATE   NOT NULL,
  last_seen_on  DATE   NOT NULL,
  is_tracked    BOOLEAN NOT NULL DEFAULT TRUE
);

-- 가격 이력: 상품 × 날짜 하루 1행 (재실행 멱등)
CREATE TABLE price_history (
  taca_item_id   BIGINT  NOT NULL REFERENCES products,
  observed_on    DATE    NOT NULL,
  display_price  INTEGER NOT NULL,
  original_price INTEGER,
  discount_rate  INTEGER,
  is_sold_out    BOOLEAN NOT NULL,
  review_score   NUMERIC(2,1),
  review_count   INTEGER,
  source         TEXT    NOT NULL,   -- BEST | CATEGORY | DEAL | DETAIL
  PRIMARY KEY (taca_item_id, observed_on)
);

-- 하루특가 편성 이력 (end_at은 특가 API에만 있다)
CREATE TABLE deal_slots (
  taca_item_id BIGINT      NOT NULL REFERENCES products,
  observed_on  DATE        NOT NULL,
  end_at       TIMESTAMPTZ,
  deal_price   INTEGER     NOT NULL,
  PRIMARY KEY (taca_item_id, observed_on)
);

-- 쉐어링크 캐시 (한 번 발급하면 영구 재사용)
CREATE TABLE sharelinks (
  taca_item_id BIGINT      PRIMARY KEY REFERENCES products,
  short_url    TEXT        NOT NULL,
  origin_url   TEXT        NOT NULL,
  issued_at    TIMESTAMPTZ NOT NULL
);

CREATE TABLE categories (
  category_id  BIGINT PRIMARY KEY,
  parent_id    BIGINT,
  level        INTEGER NOT NULL,
  display_name TEXT    NOT NULL
);

-- 수집 실행 로그 (한도 소진·실패 추적)
CREATE TABLE crawl_runs (
  id            BIGSERIAL   PRIMARY KEY,
  started_at    TIMESTAMPTZ NOT NULL,
  finished_at   TIMESTAMPTZ,
  products_seen INTEGER     NOT NULL DEFAULT 0,
  links_issued  INTEGER     NOT NULL DEFAULT 0,
  status        TEXT        NOT NULL,   -- OK | QUOTA | ERROR
  note          TEXT
);

CREATE INDEX idx_history_item ON price_history(taca_item_id, observed_on DESC);
CREATE INDEX idx_products_tracked ON products(is_tracked, last_seen_on);
```

`PRIMARY KEY (taca_item_id, observed_on)` 덕에 **같은 날 수집기를 여러 번 돌려도 안전하다**(UPSERT).
초판에 있던 `slug` 컬럼은 URL이 없어졌으므로 제거했다.

## 6. 수집기 (`@Scheduled`, 일 1회)

### 핵심 통찰 — 목록 조회가 곧 이력이다

베스트·카테고리·특가 **목록 조회 응답에 이미 가격이 들어 있다.** 따라서 랭킹에 계속 드는 상품은 목록을 훑는 것만으로 이력이 쌓이고 **추가 비용이 0이다.**

`상품 상세 조회`는 **랭킹에서 빠진 추적 대상에만** 쓴다. 10,000 한도를 가장 아껴 쓰는 방법이다.

### 실행 순서 (우선순위 = 놓치면 영영 못 보는 순)

| 순서 | 대상 | 이유 |
|---|---|---|
| 1 | **하루특가 전량** | 매일 편성이 바뀐다. 오늘 안 받으면 영영 못 본다. 검증 1순위 대상 |
| 2 | **전체 베스트** | 신규 발견 + 이력 갱신을 동시에 |
| 3 | **카테고리 베스트 순회** | 롱테일 발견. 카테고리별 커서를 저장해 다음 날 이어받는다 |
| 4 | **누락 추적 대상 보충** (상품 상세) | 1~3에서 안 잡힌 `is_tracked` 상품. 남은 한도만큼만 |

한도 소진 시 그 단계에서 멈추고 `crawl_runs.status='QUOTA'`로 기록한 뒤 다음 날 커서부터 이어간다.

> ⚠️ **단계별 한도 배분은 API 승인 후 1차 실측으로 확정한다.** 카테고리 트리 크기와 하루특가 편성 규모를 모르는 채로 숫자를 박으면 틀린다.

### 추적 대상 은퇴

추적 상품이 한도에 근접하면 **`last_seen_on`이 가장 오래된 것부터** `is_tracked=false`로 내린다. 이력은 지우지 않는다.

### 실패 처리

- HTTP 429 → `Retry-After` 존중 후 재시도
- 5xx → 지수 백오프 3회, 실패 시 해당 단계 스킵
- `SHARELINK_OPENAPI_ACCESS_DENIED` → **즉시 중단하고 알린다.** IP 변경이나 키 만료라 재시도가 무의미하다
- `resultType`을 반드시 확인한다. **HTTP 200이어도 `FAIL`일 수 있다**

## 7. 판정 로직 — 제품의 핵심

서버(Java)에만 둔다. 미니앱은 계산 결과만 받아 그린다. **로직이 두 벌이 될 여지를 만들지 않는다.**

```
Verdict verdict(List<PricePoint> history, PricePoint today)
boolean  inflatedOriginal(List<PricePoint> history, PricePoint today)
```

**규칙**

- 관측일 수 < 14 → `INSUFFICIENT`. 화면에는 *"N일째 추적 중"* 을 표시한다
- `min90` = 지난 90일 관측치의 최저 `display_price`
- `today < min90` → `ALL_TIME_LOW` (역대 최저가)
- `today <= min90 × 1.02` → `NEAR_LOW` (2% 이내는 같은 가격으로 본다)
- 그 외 → `CHEAPER_BEFORE` + 최저가와 그 날짜를 함께 보여준다

**`inflatedOriginal`**: `original_price`가 관측 이력에서 실제 `display_price`로 나타난 적이 **한 번도 없으면** 뻥튀기로 본다. "원가 10만원"이라면서 10만원에 판 적이 없는 경우다.

**하루특가 전용 판정**: 오늘 편성된 상품인데 `deal_price`가 어제 `display_price`와 같으면 → *"오늘만 이 가격"이라지만 어제도 같은 가격이었습니다.*

**엣지 케이스**

- 품절 기간의 관측치도 이력에 포함한다 (가격 자체는 유효)
- 수집 실패로 생긴 공백은 그 날이 없는 것으로 처리. 최저가 계산에 영향 없음
- `display_price <= 0` 이거나 `original_price < display_price` 인 비정상 응답은 이력에 넣지 않고 `crawl_runs.note`에 기록

**이 두 함수가 TDD 대상 1순위다.**

## 8. API

로그인이 없으므로 전부 공개 읽기 전용이다.

| 엔드포인트 | 내용 |
|---|---|
| `GET /api/deals` | 오늘의 하루특가 + 마감 시각 + 판정 |
| `GET /api/best` | 오늘의 **진짜** 특가 — `ALL_TIME_LOW`·`NEAR_LOW`만 |
| `GET /api/products/{tacaItemId}` | 상품 상세 + 가격 이력 + 판정 + 쉐어링크 |
| `GET /api/categories` | 카테고리 트리 |
| `GET /api/categories/{id}/products` | 카테고리별 목록 |

## 9. 미니앱 화면

| 화면 | 내용 |
|---|---|
| 홈 | 오늘의 진짜 특가 + 마감 임박 하루특가 |
| 상품 상세 | **가격 이력 그래프(인라인 SVG)** · 판정 뱃지 · 역대 최저/최고 · **[토스쇼핑에서 보기]** · 대가성 문구 |
| 카테고리 | 카테고리별 목록 |

**차트는 라이브러리 없이 인라인 SVG로 그린다.** 라인 하나에 `<polyline points>`면 되고, 번들 크기가 미니앱에서는 웹보다 더 중요하다. 호버 툴팁이 필요해지면 그때 붙인다.

## 10. 수익 연동

- 링크는 **수집 단계에서 미리 발급**해 `sharelinks`에 저장한다. 런타임에 API를 호출하지 않는다
- 같은 상품은 재요청해도 기존 링크가 돌아오고 한도도 차감되지 않으므로, 캐시가 비었을 때만 발급한다
- 버튼은 `shortUrl`을 쓴다. 조회 API의 `productUrl`은 **추적되지 않는다**
- 대가성 문구를 쉐어링크가 있는 모든 화면에 고정 표시한다

## 11. 테스트 전략

TDD 대상은 순수 로직이다. I/O는 얇게 유지한다.

| 대상 | 검증 |
|---|---|
| `verdict()` | 관측일 부족 / 역대최저 / 2% 경계 / 최근에 더 쌌음 / 공백 있는 이력 |
| `inflatedOriginal()` | 원가가 이력에 있음/없음, 이력 0건 |
| 하루특가 판정 | 어제와 같은 가격 / 실제로 내려간 경우 |
| 한도 배분기 | 소진 시 중단·커서 저장·다음날 이어받기 |
| 응답 정규화 | `resultType: FAIL` / 비정상 가격 / 필드 누락 |

서버는 JUnit, 미니앱은 Vitest.

- **첫날부터 가능**: 하루특가 목록 + 마감 카운트다운 + 할인율 순위
- **14일부터**: 판정 시작
- **60일부터**: 90일 창이 차서 판정 신뢰도가 올라감

웹사이트였다면 SEO 색인 기간과 겹쳐 공백이 가려졌지만, **미니앱은 노출이 즉시 시작되므로 공백이 그대로 드러난다.** 그래서 판정 불가 구간의 화면(*"N일째 추적 중"* + 마감 카운트다운)이 초판보다 중요해졌다.

## 13. 리스크

| 리스크 | 대응 |
|---|---|

## 14. 안 하는 것

RDS·Redis·로그인·회원·웹사이트 채널·크로스 플랫폼 가격 비교(다나와 정면 충돌 + 동일 상품 식별 난제)·알림(토스 앱이 이미 하고 어트리뷰션도 안 붙는다)·Spring Batch·차트 라이브러리.
